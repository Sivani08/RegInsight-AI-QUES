Application Flow
from Inspection Evidence
to Human Review

A practical map of how the running application receives a question, routes and retrieves evidence, creates and evaluates an assessment, persists each stage, and reaches an authenticated reviewer.

Scope: This guide follows the explicit AI assessment workflow in the Evidence workspace. The existing chatbot remains a separate path and is not silently routed through this workflow.

Prepared from the current project source: FastAPI, React, PostgreSQL/pgvector, a PostgreSQL job queue, LangGraph checkpoints, and local Ollama model calls.

Local application URL: http://127.0.0.1:8018

1. Whole-application picture

The web application has two related but distinct review/analysis capabilities. The normal website serves dashboards, inspection and evidence browsing, analytics, chatbot/agent features, and human review of observation classifications. The AI assessment workflow is an explicit user-started path embedded under the selected observation in Evidence.

2. Entry point: selected observation to queued workflow

1 — Select the source record. In the Evidence workspace, the selected observation supplies its original text, observation ID, and intelligence run ID. frontend/src/reginsight/Evidence.jsx renders WorkflowReview.
2 — Start an assessment. The user edits the question if needed and presses “Start AI assessment.” frontend/src/reginsight/WorkflowReview.jsx:start() sends the question, observation_id, run_id, and require_review: true through the shared request helper.
3 — Validate/authenticate the API request. Security middleware authenticates the signed-in session, checks host/origin and request bounds, and assigns a request ID. The route validates WorkflowRequest; this workflow requires an authenticated API user.
4 — Persist before processing. POST /api/workflows calls WorkflowService.create(). It creates IDs and a RECEIVED state; repository inserts the workflow/event, and the same database transaction enqueues a uniquely keyed start job. The API responds 202 Accepted.
5 — Background execution. The browser periodically refreshes workflow status. Meanwhile worker.main() polls; jobs.claim() atomically leases a job using PostgreSQL locking. A heartbeat extends the lease while work runs.
Durability: The user-facing API does not keep the browser request open for model generation. Job queue, workflow state, event sequence, and graph checkpoint are persisted, so the worker can resume a thread instead of losing the whole workflow on a short-lived request.

Retrieval and analytics details

  • For a selected observation, the service resolves the matching record using the observation intelligence snapshot, then indexes its original observation text with provenance such as run, inspection, source file, sheet, and row.
  • RetrievalService embeds the query locally and searches one PostgreSQL corpus with vector cosine and PostgreSQL full-text ranking; hybrid mode fuses ranks. A documented keyword fallback is used for embedding/network or vector data failures.
  • Retrieval trace records candidates, selected chunk IDs, filters, status, model/version and thresholds. Similarity is a cosine score, not a calibrated probability.
  • Questions asking for counts/rates/trends invoke the existing dashboard analytics service; model receives labeled deterministic D1 result, not permission to invent SQL or numerical answers.
  • Specialists: EvidenceAgent, InspectionAssessmentAgent, and DataAnalyticsAgent. Combined analytics + observation work is sequential and bounded; no autonomous recursive agent delegation.

4. Generation, evaluation, and human gate

Specialist generation

backend/agents/specialists.py loads the generation prompt and calls StructuredLLM.generate(). The client restricts generation to a local model name, bounds prompt size, uses a single-call concurrency gate, requests schema-constrained JSON, and validates the resulting Pydantic output. The specialist checks citation IDs and rejects unsupported numerical claims.

Separate judge evaluation

backend/workflows/evaluation.py makes a distinct judge-model call using the rubric prompt. Eight dimensions are scored: relevance, groundedness, factual consistency, completeness, domain correctness, safety, evidence coverage, and clarity. The system calculates the mean score and applies configured pass/revision thresholds plus hard minimum groundedness and safety checks. Same-model generator/judge is disclosed because errors may be correlated.

Why the human gate is triggered

  • Risk level is HIGH or CRITICAL (mandatory policy floor).
  • The user explicitly asks for review; the Evidence panel sets this for selected-observation assessments.
  • Retrieval is a WEAK_HIT, or this is already a human-review revision.

On a passing judge result with review required, the artifact is versioned and marked PENDING; workflow status becomes AWAITING_HUMAN_REVIEW. The graph pauses at its durable interrupt. A draft or passing score alone is not a final response.

Authenticated review and continuation

  1. Reviewer obtains pending work from GET /api/workflows/reviews/pending, or opens the selected workflow.
  2. UI displays the draft, evaluation, citations, retrieved evidence, limitations, routing/risk, and prior review history.
  3. Reviewer chooses approve, modify, or reject and provides rationale. API role must be reviewer/admin; the service uses the authenticated principal as authoritative reviewer identity.
  4. Request includes the current workflow revision, artifact version, and idempotency key. Server checks role, state, revision, artifact version, and duplicate-key consistency to prevent stale or replayed decisions.
  5. Decision and event are saved transactionally; a resume job is queued. Approve/modify marks the artifact approved. Reject can cause a bounded new generation when iterations remain.
  6. Worker resumes the LangGraph checkpoint with the persisted review ID. The graph verifies it exists; approval proceeds to finalization. Final response is either the approved artifact or reviewer-modified text.
Modification behavior: Reviewer replacement text gets deterministic checks for unsupported numbers and prohibited conclusions. The current implementation does not call the LLM judge again after a reviewer modification; the authorized reviewer is the approving gate.
Release rule: finalize() refuses to publish unless evaluation passed and any required human decision is approved for the current artifact.

5. Debugging: follow one workflow end to end

A. Confirm runtime health (PowerShell)

Set-Location "C:\Users\nitis\OneDrive\Desktop\RegInsight-AI" docker compose ps Invoke-RestMethod http://127.0.0.1:8018/api/health

Expect app and worker running, database healthy, and API health to report PostgreSQL plus a loaded dataset. If startup/import is in progress, inspect migration logs; a clean launch still has to load the prepared data.

B. Follow background execution

docker compose logs -f worker docker compose logs -f app docker compose logs --tail=100 migrate docker compose top worker

Worker logs include structured job failures and workflow_node messages with workflow ID, request ID, node/event name, and revision. App security middleware logs HTTP request ID, route, status, user ID, and elapsed time. Do not print .env or credentials to logs/chat.

C. Inspect from the application

While a workflow is open, the Evidence panel refreshes every 2.5 seconds. “Open complete operational trace” links to GET /api/workflows/{id}/trace, which returns route/risk, retrieval trace/history, D1 tools, agent outputs, artifacts and judge results, human decisions, current status, final response, and ordered events.

Common debugging interpretation

  • Still RECEIVED / no worker progress: check worker container, queue job status/lease, and worker logs.
  • ROUTED or retrieval stuck: check reference index, observation selection/run ID, local embedding service, and PostgreSQL connectivity.
  • GENERATING/EVALUATING delayed: local Ollama may be loading a model; calls are sequential, schema-bounded, and have a configured timeout.
  • REVISION_REQUIRED: inspect the latest judge issues and iteration count; correction attempts are capped by policy.
  • AWAITING_HUMAN_REVIEW: this is a deliberate pause, not a hung workflow. Reviewer/admin must decide on the exact artifact version.
  • FAILED: inspect workflow error, last event and background job error. Transient network/timeout/database operational failures are retried within job limits; other exceptions are surfaced as failures.

Quick mental model: React submits; FastAPI authenticates and records; PostgreSQL queues; worker executes; graph checkpoints; routing decides; retrieval/analytics supply evidence; specialists draft; judge evaluates; policy pauses for a human where required; authenticated review persists a decision; worker resumes; finalization enforces the approval gate.

This guide documents current source behavior, not regulatory certification. Scores and local model outputs are decision support only. Always inspect source evidence and have a qualified human reviewer make regulatory decisions.
